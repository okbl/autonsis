# Что удалось выяснить про НСИС по сохранённой странице и PDF

Источник: сохранённая страница `https://lk.nsis.ru/requestLog/` со всеми
ресурсами и один реальный PDF-ответ (`history_22.09.2026_09_18_13.pdf`,
36 страниц). Всё ниже получено разбором этих двух файлов, без обращения к
сайту.

Главный вывод: **личный кабинет НСИС — обычное React-приложение поверх
JSON-API. Никакого разбора вёрстки и нажатия кнопок не требуется.**

## API

Конфигурация приложения лежит в атрибуте `data-js-app` на `<body>`:

```json
{"apiUrl":"https://bff.nsis.ru","cabinetLink":"https://lk.nsis.ru/","isAuth":true}
```

Клиент ходит в API так (видно в `bundle.js`): `credentials: "include"`,
заголовок `X-Requested-With: XMLHttpRequest`, база — `https://bff.nsis.ru`.
Значит код, выполняемый на странице `lk.nsis.ru`, может делать ровно те же
запросы с той же сессией.

Нужные точки входа:

| Назначение | Метод и путь |
| --- | --- |
| Профиль текущего пользователя (кто сейчас работает) | `GET bff/profile` |
| Журнал обращений | `GET bff/bff-query-log/request-log?limit=&offset=&sortDirection=desc` |
| Ответ в PDF | `GET bff/insurance-history/pdf?fileId=&signId=` |
| Тот же ответ в JSON | `GET bff/insurance-history/json?fileId=&signId=` |
| Выход | `POST bff/logout` |

Журнал принимает ещё `requestIds[]`, а на странице есть фильтры
`requestStatus`, `signatureStatus`, `period`, `q` — те же имена уходят в
запрос.

Форма ответа журнала (восстановлена по коду разбора):

```js
{ queries: [ {
    requestId, createDate,
    status: { code },                 // "done" | "error" | "bsi_done_data_not_found" | ...
    answers: [ { json: {fileId, signId, fileSize},
                 pdf:  {fileId, signId, fileSize} } ]
} ] }
```

Файл считается готовым, если `fileId`, `signId` заданы и `fileSize > 0` —
это ровно та проверка, которой пользуется сам сайт. Отсюда и определение
«новый готовый ответ»: статус `done` и валидный `pdf` в `answers[0]`.

Часть запросов сайт подписывает заголовком `X-Inssys-Signature` (создание
нового запроса, отправка на почту). Для скачивания уже готового ответа
подпись в коде необязательна — но это единственное место, которое стоит
проверить на живом сайте, потому что подделать подпись УКЭП мы не можем и
не будем.

## Что внутри PDF

Разобрал текстовый слой самостоятельно — zlib-распаковка потоков плюс
разбор карт `ToUnicode`. Работает, получилось около 120 строк кода и ни
одной внешней библиотеки. **pdf.js не нужен.**

Страница 1 — сопроводительное письмо, и в нём есть всё, чего не хватало:

```
Щенников Алексей Дмитриевич          ← финансовый управляющий (адресат)
Email: …
№ Дела: А50-26151/2025               ← номер дела, который «нельзя получить»
… в ответ на запрос в отношении Борцов Николай Валерьевич,
Борцова Любовь Андреевна сообщает следующее.
… от 15.09.2026
```

Страница 2 — начало приложения, и там субъект указан ещё точнее:

```
Субъект, в отношении которого запрошена страховая история:
Физическое лицо - Борцов Николай Валерьевич 15.03.1991 года рождения
```

То есть из PDF извлекаются: **ФИО должника (и дата рождения), номер дела,
ФУ, дата ответа**. Один ответ может касаться нескольких лиц сразу — в
примере это супруги, и в приложении на каждого свой раздел.

Приложение содержит договоры страхования: серия и номер полиса, страховщик,
страхователь и его паспорт, марка и госномер ТС, VIN, собственник,
допущенные к управлению. В разобранном примере большая часть договоров —
чужие, где должник лишь вписан в число водителей.

## Что это меняет

* **ФИО берём из PDF надёжно**, а не угадываем. В списке обращений ФИО нет
  вообще — там только тип запроса, статус и дата, так что разбор PDF
  обязателен; хорошая новость в том, что он оказался простым.
* **Номер дела доступен.** Ограничение «в первой версии номер дела не
  используется» снимается: он печатается в ответе и попадёт в имя файла.
* **Скачивание не требует нажатия кнопок** — файл забирается запросом по
  `fileId`/`signId`, сразу в память, с правильным именем.
* **Текущий ФУ определяется автоматически** — из `bff/profile` и
  перекрёстно из адресата в самом PDF.
* **Дубликаты — по `requestId`**, точно и до скачивания.
* Обычная папка «Загрузки» в схеме больше не участвует.

## Что ещё предстоит проверить на живом сайте

1. Ответ `bff/profile` и одна запись `request-log` целиком — вдруг ФИО и
   номер дела есть уже там, тогда разбор PDF становится лишь запасным путём.
2. Скачивается ли PDF без заголовка `X-Inssys-Signature`.
3. Работают ли на `lk.nsis.ru` закладки (`javascript:`) и доступ страницы к
   папке (File System Access API) — от этого зависит способ доставки кода.
4. Отдельно стоит убедиться, что автоматизация собственного доступа не
   противоречит регламенту НСИС: запросы те же самые, что делает сам
   личный кабинет, но выполняет их программа.
