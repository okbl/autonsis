# Автоскачивание ответов НСИС — архитектура MVP

Документ отвечает на один вопрос, от которого зависит всё остальное: **каким
реально работающим способом можно управлять Chromium GOST и НСИС в этой
корпоративной среде** — без расширений, без `.bat`/`.cmd`/PowerShell, без
Python/Node, без облака. Дальше — из этого ответа выводится архитектура.

## Вывод, если читать только один абзац

Без локального компонента задача не решается. Всё, что делает приложение
после скачивания — читает PDF, переименовывает, раскладывает по папкам,
ведёт журнал, считает hash, ждёт интервал, работает после простоя — это
операции с файловой системой и фоновая работа. В браузере без расширения
их нет, а расширения и скрипты запрещены. Значит нужен **один
подписанный портативный `.exe`**, разрешённый администратором однократно.
Права администратора при работе не нужны: ни службы, ни драйвера, ни
правила фаервола, ни изменения политик браузера.

Хорошая новость: этому `.exe` не нужно самому уметь ГОСТ-TLS и не нужно
касаться УКЭП. Он управляет уже авторизованным браузером и **все запросы
к НСИС выполняет внутри браузера** — браузер остаётся единственным
участником, который знает про криптографию.

## Почему не получится проще

Перебор всех вариантов, которые в этих ограничениях вообще приходят в
голову, с вердиктом по каждому.

| Вариант | Вердикт |
| --- | --- |
| Расширение браузера | Запрещено условием задачи. |
| Свой HTTP-клиент к НСИС по cookie из профиля браузера | **Не работает.** Chromium GOST используется именно потому, что канал ГОСТовый: обычный TLS-стек (WinHTTP, SChannel, .NET, Go) ГОСТ-шифрсьюты не умеет, сессию не поднимет. Плюс cookie в свежих сборках Chromium защищены App-Bound Encryption, а в Windows — DPAPI; лазить туда в корпоративной среде плохая идея и без ГОСТа. |
| Автоматизация мышью/клавиатурой (SendInput) | Технически возможно без флагов, но это самый хрупкий вариант: ломается от прокрутки, фокуса, случайного клика пользователя, разрешения экрана. Не годится как основа, годится как последнее средство. |
| UI Automation / дерево доступности Chromium | Стабильнее SendInput, но всё равно читает интерфейс, а не данные, и не даёт управлять загрузками. Оставляем в резерве. |
| Chromium GOST + DevTools Protocol (CDP) | **Рабочий вариант.** Chromium GOST — обычный Chromium, CDP в нём есть. Нужен один флаг при запуске браузера, флаг ставит наше приложение, когда само запускает браузер. |
| Планировщик Windows вместо резидентного приложения | Планировщик умеет запускать только программу — то есть тот же `.exe`. Ничего не экономит. |
| Букмарклет (`javascript:` в закладке) | Единственный путь **совсем без установки**. Сильно урезанный, см. отдельный раздел. |
| Готовый Selenium/Playwright/Puppeteer | Это Node/Python плюс драйвер — запрещено. Свой CDP-клиент внутри `.exe` — это WebSocket и JSON, тут не нужна библиотека. |

## Как приложение управляет Chromium GOST

**1. Браузер запускает приложение, а не пользователь.** В панели кнопка
«Открыть НСИС». Приложение стартует `chromium-gost.exe` с тремя флагами:

```
--remote-debugging-port=0            (порт отдаётся ОС, читаем из DevToolsActivePort)
--remote-allow-origins=http://127.0.0.1
--user-data-dir=<свой профиль>
```

Отдельный профиль — не прихоть: в сборках Chromium начиная с 136-й
отладочный порт намеренно не включается на профиле по умолчанию, чтобы
сторонняя программа не могла подсесть к обычному сеансу пользователя.
Порт слушается только на loopback.

**2. Пользователь входит по УКЭП руками.** В этом окне он видит обычный
НСИС и обычное окно выбора сертификата. Приложение не видит ни пароля, ни
контейнера, ни приватного ключа — оно вообще не участвует в аутентификации.

**3. Дальше приложение работает внутри этой страницы.** Через CDP
(`Runtime.evaluate` с `await fetch(...)`) выполняется код в контексте
открытой вкладки НСИС. Это значит: те же cookie, тот же ГОСТ-канал, те же
заголовки — сервер не отличает наш запрос от обычного действия
пользователя в интерфейсе. PDF возвращается в приложение как base64,
приложение само решает, как его назвать и куда положить. Никакого
«менеджера загрузок» и папки «Загрузки» в этой схеме нет.

**4. Если в НСИС нет пригодного API** (список отдаётся страницей, а
«Скачать» — это кнопка с одноразовым токеном), работает второй режим: CDP
нажимает кнопку, а загрузка перехватывается
(`Browser.setDownloadBehavior: allowAndName` — файлы падают во временную
папку под именем-GUID, событие `Browser.downloadProgress` сообщает о
завершении). Приложение забирает файл из временной папки, читает,
переименовывает, раскладывает. Пользовательская папка «Загрузки» не
засоряется.

Оба режима — это одна и та же прослойка «адаптер НСИС» с двумя
реализациями. Какой включится по умолчанию, решается после того, как я
увижу, как устроен раздел «Обращения» (см. «Что нужно от вас»).

**5. Сессия.** Перед каждой проверкой — дешёвый запрос профиля. `401`,
редирект на вход или исчезнувший маркер авторизации = «Сессия истекла»:
проверки останавливаются, панель показывает статус и кнопку, которая
поднимает окно браузера на вход. Приложение опрашивает страницу раз в
несколько секунд; как только сессия снова живая — читает ФИО ФУ из
профиля НСИС и само продолжает с того места, где остановилось.

**6. Если браузер закрыли.** Приложение это видит (обрыв WebSocket) и
переходит в состояние «НСИС недоступна / нужен вход» — без ошибок и без
попыток что-то нажимать.

## Что нужно от администратора (минимум)

Ровно один пункт: **разрешить запуск одного подписанного `.exe`**
(правило AppLocker/SRP по издателю или по хешу, либо размещение файла в
уже разрешённой папке).

Не нужно: прав администратора при работе, установки в `Program Files`,
службы Windows, задания в планировщике, правил фаервола (loopback фаервол
не фильтрует), изменения политик Chromium, установки расширений,
установки .NET/Node/Python, доступа в интернет куда-либо кроме самого
НСИС через браузер.

Автозапуск — ярлык в папке автозагрузки пользователя (`shell:startup`),
это пользовательская папка, администратор не нужен.

## План Б: если `.exe` не разрешат вообще

Тогда остаётся букмарклет: закладка с `javascript:`-кодом, которую ФУ
нажимает на странице «Обращения». Это не расширение и не скрипт-файл.
Что он может: найти готовые ответы, скачать их тем же `fetch` в контексте
страницы, показать поверх страницы свою панель, и — через File System
Access API — записать файлы в папку, которую пользователь один раз
выбрал в диалоге.

Чего он не может, и это не обходится:

* работать, когда браузер закрыт или страница не открыта — значит
  «проверять раз в N минут» и «догнать за три дня простоя» отпадают,
  остаётся «нажать кнопку»;
* надёжно хранить журнал — только IndexedDB домена НСИС, которая
  стирается при очистке данных браузера;
* разобрать PDF без внешних библиотек — pdf.js придётся встраивать в
  саму закладку, это километровый URL;
* выжить при Content-Security-Policy сайта — многие сайты букмарклеты
  этим просто блокируют, и проверить это можно только на живом НСИС.

Честная оценка: это автоматизирует пункты 4–7 и превращает 2–3 в один
клик, но приложением из задания не является. Предлагаю держать как
резерв, а не как основной путь.

## Архитектура MVP

Один процесс, шесть частей, между ними — явные границы, чтобы каждую
можно было тестировать отдельно.

```
┌─────────────────────────── agent.exe (один процесс) ───────────────────────────┐
│                                                                                │
│  Панель (HTTP на 127.0.0.1)  ←──JSON──→  Ядро/планировщик                      │
│        HTML+CSS+JS внутри exe                 │                                │
│                                               ├── Адаптер НСИС ──CDP──→ Chromium GOST ──ГОСТ-TLS──→ НСИС
│                                               ├── Извлечение ФИО из PDF        │
│                                               ├── Хранилище файлов (папки/имена)│
│                                               └── Журнал (события + состояние) │
└────────────────────────────────────────────────────────────────────────────────┘
```

* **Ядро/планировщик** — интервал с небольшим разбросом, «Проверить
  сейчас», «Остановить автопроверку», очередь задач, 3–5 параллельных
  загрузок (число настраивается), повторы с возрастающей паузой. Ошибка
  одного файла помечает только его: задача снимается с очереди, остальные
  продолжают.
* **Адаптер НСИС** — единственное место, которое знает про разметку и
  адреса сайта. Меняется НСИС — правится один файл.
* **Извлечение ФИО** — чистая функция «байты PDF → ФИО или пусто», без
  файловой системы и сети: так её можно прогнать по реальным PDF в
  тестах, как в ОКБ-анализаторе.
* **Хранилище** — атомарная запись (временный файл + переименование),
  чтобы при обрыве не осталось битого PDF с правильным именем.

## Файлы, имена, папки

По умолчанию `Рабочий стол\НСИС\20.09.2026\`, папка на каждый день (дата
скачивания), путь меняется в настройках. Ничего не удаляется автоматически.

`Иванов Иван Иванович — 20.09.2026 14-35-12.pdf`, при неудаче —
`Не определено — 20.09.2026 14-35-12.pdf`. Символы, запрещённые в именах
Windows, вычищаются; длина имени ограничивается с запасом на длинный путь.
При совпадении имени (тот же ФУ, та же секунда) добавляется ` (1)`, ` (2)`
— тот же механизм, что при ручном повторном скачивании.

## Дубликаты: hash — не единственный ключ

Тут есть тонкость, о которой стоит сказать прямо: **по hash содержимого
нельзя понять, что файл не нужно скачивать** — чтобы посчитать hash, его
уже надо скачать. Поэтому два уровня:

1. **До скачивания** — идентификатор обращения/ответа из списка НСИС.
   Обращение уже обработано → не скачиваем вовсе. Это и есть «при
   обычной автопроверке повторно не скачивать».
2. **После скачивания** — SHA-256 содержимого. Ловит случай, когда тот же
   ответ пришёл под другим идентификатором: файл не сохраняется второй
   раз, в журнале появляется статус «Пропущено — дубликат».

Оговорка: если НСИС проставляет в PDF время выгрузки, побайтовый hash у
одного и того же ответа будет разным при каждом скачивании — тогда
второй уровень перестанет ловить дубликаты, а первый продолжит работать.
Проверим на реальных файлах.

Кнопка «Скачать повторно» в журнале обходит оба уровня и всегда создаёт
новый файл: `Файл (1).pdf`, `Файл (2).pdf`.

## Откуда брать ФИО

Порядок, от надёжного к запасному:

1. **Из списка «Обращения»** — если в строке обращения видно ФИО
   должника, это точнее любого разбора PDF, потому что это ровно то, что
   ФУ сам вводил в запрос. Если так — PDF разбирать вообще не нужно,
   разбор остаётся страховкой.
2. **Из текстового слоя PDF** — по меткам («в отношении», «Субъект»,
   «ФИО», «Фамилия, имя, отчество») с проверкой формы слов; затем — по
   узнаваемому шаблону трёх слов с кириллическими окончаниями.
3. **Ничего не нашли** — `Не определено`, статус «Не удалось определить
   ФИО», файл всё равно сохранён и виден в журнале. Никогда не теряем файл
   из-за неудачного разбора.

Если ответы приходят сканами без текстового слоя, распознавание (OCR) в
MVP не делаем: внешние сервисы запрещены, а встроенный OCR — отдельная
история на потом. Такие файлы получают `Не определено`.

## Несколько ФУ и приватность

ФУ определяется после авторизации по профилю НСИС — отображаемое имя и
стабильный идентификатор. Больше ничего: ни сертификатов, ни контейнеров,
ни паролей, ни отпечатков УКЭП приложение не читает и не хранит. Каждая
запись журнала помечается тем ФУ, под которым получена. Смена ФУ =
обычная смена сессии: приложение замечает нового пользователя и меняет
пометку для новых записей, старые не трогает.

Данные лежат в профиле пользователя Windows. В журнале есть ФИО должников
— это персональные данные, поэтому папка журнала описана в настройках
явно, и никуда наружу ничего не уходит.

## Журнал

Журнал — **append-only файл событий** плюс собранное из него текущее
состояние. Так проще: нет базы, которую можно повредить, файл читается
глазами, история попыток получается сама собой.

Запись ответа: ФИО, дата/время, имя файла, полный путь, ФУ,
идентификатор обращения, hash, статус, количество попыток, текст ошибки.
У успешных — только итог. У ошибок — все попытки: когда, что случилось,
что вернул сервер.

Статусы: `Скачано`, `Пропущено (дубликат)`, `Ошибка`, `ФИО не определено`.
Ошибки человеческим языком — «НСИС недоступна», «Сессия истекла», «Ошибка
скачивания», «Не удалось определить ФИО»; техническая подробность
прячется под «показать детали» для разбора инцидентов.

Число повторов и пауза между ними настраиваются.

## Работа после простоя

При старте приложение не полагается на «что было в прошлый раз»: оно
проходит список «Обращения» целиком (с постраничной подгрузкой),
вычитает уже обработанные идентификаторы и берёт в работу остальные.
Поэтому неважно, был простой два часа или две недели.

## Панель

Локальная страница на `127.0.0.1`, оформление — как в ОКБ-анализаторе:
алебастровый фон, тёплый грейж поверхностей, угольный текст, терракота
как единственный акцент, Onest, плиточная раскладка, где размер плитки
задаёт важность. Цвет несёт смысл: терракота — требует внимания,
кирпичный — ошибка, олива — только как крайняя точка шкалы «всё в
порядке». Шрифт встроен в `.exe` — интернета у страницы нет.

Главный экран: текущий ФУ, статус НСИС, новых ответов, скачано сегодня,
ошибок, пропущено, последние ответы, «Проверить сейчас», «Остановить
автопроверку».

Журнал: поиск по ФИО, поиск по имени файла, фильтры по дате, статусу и
ФУ, «Открыть PDF», «Открыть папку», «Скачать повторно», детали ошибок.

Настройки: путь хранения, интервал проверки, число параллельных
загрузок, число повторов, путь к `chromium-gost.exe`.

Ни всплывающих уведомлений Windows, ни автоматического открытия папок и
PDF после загрузки — как просили.

## Безопасность локальной панели

Панель слушает loopback, но на loopback может постучаться и любая
страница, открытая в браузере. Поэтому: проверка `Origin`, токен сессии,
лежащий в файле рядом с приложением, и отказ на любой кросс-доменный
запрос. Иначе сайт в соседней вкладке смог бы дёргать наше API.

Запуск в единственном экземпляре (именованный мьютекс) — два процесса на
одну папку и один журнал не должны попасть.

## Стек

Требования к стеку жёсткие: один файл, без установки рантайма, маленький,
подписываемый, с нормальным разбором PDF и без http.sys (`HttpListener`
без прав администратора не поднимается — слушаем обычный сокет).

Этому отвечают два варианта:

* **.NET Framework 4.8** — есть в любой Windows, `.exe` на пару мегабайт,
  ничего доустанавливать не надо, PDF разбирает PdfPig, иконка в трее и
  диалоги — из коробки. Самый предсказуемый вариант для корпоративной
  машины.
* **Go** — один статический `.exe`, тоже без рантайма, но извлечение
  текста из PDF в экосистеме Go заметно слабее, а ФИО мы берём именно из
  текста.

Выбор — за вами, по умолчанию предлагаю первый.

## Что нужно от вас, чтобы двигаться дальше

1. Разрешение на один подписанный `.exe` (или прямой ответ «нельзя» —
   тогда делаем план Б с его ограничениями).
2. Как устроен раздел «Обращения»: HAR-файл сетевых запросов или хотя бы
   скриншоты и HTML страницы. От этого зависит, работаем мы через `fetch`
   или через нажатие кнопок.
3. Видно ли в списке обращений ФИО должника. Если да — разбор PDF
   перестаёт быть основным путём, и надёжность заметно вырастает.
4. Пример PDF-ответа (можно с вымышленными данными, но с той же
   структурой) — без него извлечение ФИО пишется наугад.
5. Версия Chromium GOST и то, как выполняется вход: прямо сертификатом
   или через Госуслуги. Плюс: работает ли вход в свежем профиле браузера
   — если для подписи нужен плагин КриптоПро, установленный расширением,
   отдельный профиль может его не увидеть.

6. Прогон на живом НСИС, доводка формулировок ошибок.
